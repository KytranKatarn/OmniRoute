## Verify-before-build findings (live code)

- `replay_job` slice-1 path: re-entrant single-item caps → re-dispatch; everything else → clone `pending` + `metadata.replay_needs_handler` (a pending clone is **never** auto-run because there is **no generic poller** of pending `bridge_jobs`).
- Richest multi-step job family = **consciousness backlogs**: `batch_embedding` / `batch_analysis` / `translate_batch`, created via `dispatcher.create_job(..., total_steps=len(items))` and run by an **immediately-spawned daemon thread** (`tools/consciousness/processing_routes.py`).
- These are **idempotent**: re-running re-selects only unprocessed rows (`WHERE embedding IS NULL` / `ai_analysis IS NULL` / missing translation keys).
- Reusable re-kick entrypoint already exists: **`_trigger_loop_op(op)`** (processing_routes.py:1196) — docstring "no Flask context needed", opens its own DB conn, spawns a `daemon` thread and **returns immediately** (non-blocking), `if not items: return` (no-op on empty backlog), and `create_job` dedups (re-trigger while a job runs = safe no-op). `jt_map`: `batch_analysis→analysis`, `batch_embedding→embedding`, `translate_batch→translate`.

→ A resume handler for these job_types = call `_trigger_loop_op(op)`. Genuinely resumes the interrupted backlog's remaining work, safe + non-blocking + idempotent. Real, not aspirational.
