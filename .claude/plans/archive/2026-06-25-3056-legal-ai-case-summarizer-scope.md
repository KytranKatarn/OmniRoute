## Locked decisions (do not relitigate)

1. **Content types at launch = ALL THREE:** SCC decisions (`scc_decisions`), regulations (`regulations`, Canada Gazette), ethics rulings (`ethics_rulings`, CIEC).
2. **Generation = ON-DEMAND + CACHE.** First view dispatches to G.A.V.E.L. in a background daemon thread, caches the result; later views are instant. **NO bulk pre-generation** in this scope.
3. **Tier gate = SOLO+ across all three content types.** This is a deliberate choice to gate the *AI-compute* value (the summary), NOT a mirror of an existing uniform tier gate. **The underlying list endpoints are NOT uniformly gated** (corrected — see §3.1): `/api/scc/decisions` (`scc.py:17`), `/api/ethics` (`ethics.py:16`) and `/api/competition` (`competition.py:19`) carry `@tier_required("solo")`, but **`GET /api/regulations` (`regulations.py:8`) is fully PUBLIC — no auth, no tier gate.** We deliberately gate AI summaries at SOLO+ even for regulations, accepting the asymmetry that regulation *data* is public while AI *summaries* of it are paid (the AI compute is the gated value).

## 1. Goal & user story

**Goal:** Give Legal Watch subscribers a one-click, plain-language AI summary — with a "significance / precedent impact" line — for any individual record across all three legal-content surfaces (SCC decisions, Canada Gazette regulations, CIEC ethics rulings), generated by G.A.V.E.L. over the mesh and cached so repeat views are instant.

**User story:**
> As a SOLO+ Legal Watch subscriber browsing the Court / Regulations / Ethics tabs, I click "Summarize" on a row. The row expands inline; G.A.V.E.L. produces (a) a plain-language summary, (b) a significance/precedent-impact note, and (c) a few key points. The first click shows a "G.A.V.E.L. is analyzing…" state and resolves within ~tens of seconds; every later click for that same record is instant (served from cache).

**Constraints baked into the story:**
- Ethics + SCC summaries are **defamation-sensitive** — they describe only the published CIEC finding / the court's own outcome, never asserting guilt or wrongdoing beyond the source's stated conclusion.
- Source text is thin for some types (see §4 and §9) — the prompt must forbid fabrication.
- Tier gate is explicit per endpoint (§3.1), NOT inherited from a uniform list-endpoint gate (decision #3): regulations data is public, regulation summaries are SOLO+.

## 2. Data model — single unified cache table `ai_summaries`

One table shared by all three content types, keyed by `(content_type, source_id)`. This matches the shared-component frontend (§5) and the single backend endpoint (§3). Confirmed: every list endpoint already returns a numeric `id` — `scc_decisions.id` (`schema.sql:80`), `regulations.id` (`schema.sql:18`), `ethics_rulings.id` (`schema.sql:47`).

### 2.1 Table DDL (add to `schema.sql`, after the `competition_enforcement`/`scc_decisions` blocks ~`schema.sql:64-95`)

```sql
-- #3056 AI Case Summarizer — unified on-demand+cache for SCC / regulations / ethics
CREATE TABLE IF NOT EXISTS ai_summaries (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    content_type      TEXT NOT NULL,          -- 'scc' | 'regulation' | 'ethics'
    source_id         INTEGER NOT NULL,       -- scc_decisions.id / regulations.id / ethics_rulings.id (loose ref, NO FK — see note)
    plain_summary     TEXT,                   -- G.A.V.E.L. plain-language summary
    precedent_impact  TEXT,                   -- significance / precedent-impact note
    key_points        TEXT,                   -- JSON array string, e.g. '["...","..."]'
    model_used        TEXT,                   -- echoed from dispatch response.model
    status            TEXT NOT NULL DEFAULT 'pending',  -- pending | ready | failed
    error             TEXT,                   -- failure detail when status='failed'
    retry_count       INTEGER NOT NULL DEFAULT 0,       -- attempts so far; capped (§3.6)
    last_attempt_at   TEXT,                   -- ISO8601 UTC of the most recent dispatch attempt (cooldown + stuck-pending recovery)
    generated_at      TEXT,                   -- ISO8601 UTC when status became ready/failed
    created_at        TEXT NOT NULL,          -- ISO8601 UTC at row insert
    UNIQUE(content_type, source_id)
);
CREATE INDEX IF NOT EXISTS idx_ai_summaries_lookup ON ai_summaries(content_type, source_id);
CREATE INDEX IF NOT EXISTS idx_ai_summaries_status ON ai_summaries(status);
```

**Status vocabulary** is deliberately `pending|ready|failed` (FEATURE-mandated). Note: the Game Studio precedent (KB #275497/#275499) uses `queued→running→completed`; we collapse to 3 because there is exactly one dispatch per record — no multi-stage pipeline. `pending` covers both "row just inserted" and "thread running".

**Why a NEW table, not columns on each source table:** `CREATE TABLE IF NOT EXISTS` re-run via `executescript` (init_db) will NOT add columns to an existing `scc_decisions`/`regulations`/`ethics_rulings` — adding columns would need guarded `ALTER TABLE` + `PRAGMA table_info` checks (SCC finding flagged this). A separate cache table sidesteps that entirely and lets all 3 types share one schema + one endpoint + one component. **This table is additive-only — no migration ordering concern (§7 Phase 1, §8 verify).**

**No FK to source tables — deliberate (added per critic):** `db.py:12` sets `foreign_keys=ON`, but `ai_summaries.source_id` is a *loose* reference with NO `REFERENCES` clause. Rationale: a single cache table cannot FK to three different parents. Consequence: if a source row were deleted/re-ingested with a *new* id, the cache row would orphan. **Low risk** because SCC/regulations/ethics all re-ingest by URL **upsert** (ids are stable across re-ingest), so orphaning effectively does not occur in practice. Stated explicitly so a future ingest refactor that changes the upsert key knows to invalidate the cache.

### 2.2 Defensive `_ensure_table()` (mirror `ingest/competition.py:36-62`)

Put the DDL in the new `routes/summarize.py` module as `_DDL` + `_INDEXES` and call `_ensure_table(conn)` at the top of each handler before touching `ai_summaries` (belt-and-suspenders for fresh deploys before `schema.sql` re-runs):

```python
_DDL = """CREATE TABLE IF NOT EXISTS ai_summaries ( ... )"""   # same as 2.1
_INDEXES = (
    "CREATE INDEX IF NOT EXISTS idx_ai_summaries_lookup ON ai_summaries(content_type, source_id)",
    "CREATE INDEX IF NOT EXISTS idx_ai_summaries_status ON ai_summaries(status)",
)
def _ensure_table(conn):
    conn.execute(_DDL)
    for idx in _INDEXES:
        conn.execute(idx)
    conn.commit()
```

`schema.sql` is run at boot via `init_db()` inside `create_app()` (`app.py:84`). Because every statement in `schema.sql` is `CREATE ... IF NOT EXISTS`, running the **full** file via `executescript` against the already-populated live `legal.db` is idempotent — adding our block does not risk erroring on existing data (verified as a deploy precondition in §8).

## 3. Backend API — `routes/summarize.py` (new blueprint `summarize_bp`)

### 3.1 Endpoints

| Method · Path | Gate | Purpose |
|---|---|---|
| `POST /api/summarize` | `@tier_required("solo")` | Cached-or-kickoff. Body `{content_type, source_id}`. If a `ready` row exists → return it (200). If `pending` but **stale** (created >5 min ago — stuck/recycled worker) → treat as retryable. If no row, OR `failed` (under cap + past cooldown), OR stale-`pending` → upsert row to `pending`, **spawn daemon thread** (subject to the global generation semaphore, §6), return 202 `{status:"pending"}`. If a fresh `pending` row exists (in-flight) → return 202 `{status:"pending"}` (dedup guard, §6). If `failed` and over the retry cap → return 200 `{status:"failed", error, terminal:true}` and DO NOT re-dispatch. |
| `GET /api/summarize/status?content_type=&source_id=` | `@tier_required("solo")` | Poll. Returns `{status, plain_summary, precedent_impact, key_points, model_used, error, retry_count}` for the row, or `{status:"none"}` if absent. |
| `POST /api/summarize/regenerate` | `@tier_required("owner")` | Admin force-regen. Resets the cached row to `pending` (`retry_count=0`) and re-kicks the thread, bypassing cap/cooldown. Mirrors the owner gate on `/api/scc/ingest` (`scc.py:127`) and `/api/ethics/ingest` (`ethics.py:85`). **See gate note below — `owner` is intentional; force-regen is owner-only, matching the ingest endpoints.** |

**CORS note (no code change needed):** `app.py` `after_request` (`add_cors_headers`, `app.py:59-64`) sets `Access-Control-Allow-Methods: "GET, OPTIONS"` — **POST is not in the CORS allowlist.** This is NOT a failure for our UI because all frontend calls are **same-origin** (§5.2 builds `new URL(path, window.location.origin)`, exactly like the existing `POST /api/legal/chat` which already works same-origin). Same-origin requests succeed regardless of the response `Access-Control-Allow-Methods` header. **Only if** an external/cross-origin caller is ever added would `app.py:62` need `POST` appended to the allowlist — out of scope for the in-scope same-origin UI.

**Tier helper** (confirmed `auth.py`): `from auth import tier_required`; `@tier_required("solo")` → `required_level=30`; passes solo/team/agency/admin/owner/kytran, blocks free/viewer/pro/starter. On fail: unauth → 401 JSON `{success:False,error:"Authentication required"}`; under-tier → 403 JSON `{success:False,error:"Requires solo tier",current_tier:...}`. **Note:** `/api/` paths are exempt from the global `billing_gate` (`app.py:26`), so the explicit `@tier_required` decorator is what enforces SOLO+ here — it is mandatory, not optional.

**`owner` gate level (regenerate) — pinned:** `@tier_required("owner")` requires the highest level; per the identity rules (billing.md / gov-watch.md), `kytran`/`owner`/`admin` all resolve to the high tier and pass. The owner session (Kytran) passes. We gate regenerate on `owner` **to match the ingest endpoints it mirrors** (`scc.py:127` / `ethics.py:85` both use `@tier_required("owner")`) — verified those are `owner`, not `admin`. This is force-regen of an already-public-data summary, so owner-only is acceptable and consistent. (If a future requirement wants admin-but-not-owner force-regen, change to `@tier_required("admin")` — but that would diverge from the ingest precedent.)

### 3.3 POST `/api/summarize` flow

```python
STALE_PENDING_MIN = 5          # a 'pending' row older than this = stuck worker → retryable
RETRY_CAP = 3                  # max dispatch attempts per record (§3.6)
RETRY_COOLDOWN_SEC = 60        # min seconds between failed retries (§3.6)

@summarize_bp.route("/api/summarize", methods=["POST"])
@tier_required("solo")
def create_summary():
    data = request.get_json(silent=True) or {}
    content_type = (data.get("content_type") or "").strip()
    source_id = data.get("source_id")
    if content_type not in ("scc", "regulation", "ethics") or not isinstance(source_id, int):
        return jsonify({"error": "content_type and integer source_id required"}), 400

    # access_token MUST be captured here (request scope) and passed into the thread.
    access_token = (session.get("kytran_user") or {}).get("access_token", "")
    if not access_token:
        return jsonify({"error": "No access token in session"}), 401

    conn = get_db()
    try:
        _ensure_table(conn)
        row = conn.execute(
            "SELECT * FROM ai_summaries WHERE content_type=? AND source_id=?",
            (content_type, source_id)).fetchone()

        if row and row["status"] == "ready":
            return jsonify({"status": "ready", **_present(row)}), 200

        if row and row["status"] == "pending":
            # In-flight dedup — UNLESS the pending row is stale (worker recycled mid-gen).
            if not _is_stale_pending(row):       # created_at within STALE_PENDING_MIN
                return jsonify({"status": "pending"}), 202
            # else: fall through and re-kick (stuck pending is retryable)

        if row and row["status"] == "failed":
            # Terminal once over the cap; otherwise honor the cooldown.
            if row["retry_count"] >= RETRY_CAP:
                return jsonify({"status": "failed", "error": row["error"],
                                "terminal": True}), 200
            if not _cooldown_elapsed(row, RETRY_COOLDOWN_SEC):
                return jsonify({"status": "failed", "error": row["error"],
                                "cooldown": True}), 200
            # else: fall through and retry (under cap + past cooldown)

        # --- reachable for: no row | retryable failed | stale pending ---
        # Build the source-text payload BEFORE spawning the thread (needs DB read).
        prompt = _build_prompt(conn, content_type, source_id)
        if prompt is None:                     # missing source row OR no safe text (ethics NULL summary)
            return jsonify({"status": "unavailable",
                            "error": "No source text available to summarize"}), 200

        now = _now_iso()
        # Conditional upsert: do NOT re-kick a row that is already pending-and-fresh.
        # ON CONFLICT ... DO UPDATE ... WHERE collapses the SELECT→INSERT TOCTOU window.
        cur = conn.execute(
            "INSERT INTO ai_summaries (content_type, source_id, status, created_at, last_attempt_at) "
            "VALUES (?,?, 'pending', ?, ?) "
            "ON CONFLICT(content_type, source_id) DO UPDATE SET "
            "  status='pending', error=NULL, created_at=excluded.created_at, "
            "  last_attempt_at=excluded.last_attempt_at "
            "WHERE ai_summaries.status != 'ready' "
            "  AND NOT (ai_summaries.status='pending' "
            "           AND ai_summaries.created_at > datetime('now', ?-' minutes')) ",
            (content_type, source_id, now, now,
             f"-{STALE_PENDING_MIN}"))   # illustrative; see note
        conn.commit()
        kicked = cur.rowcount > 0          # rowcount 0 ⇒ a concurrent request already won the kick
    finally:
        conn.close()

    if kicked:
        _spawn_generation(content_type, source_id, prompt, access_token)  # respects §6 semaphore
    return jsonify({"status": "pending"}), 202
```

> Implementation note: the `WHERE` clause on `ON CONFLICT … DO UPDATE` is the key hardening (SQLite supports `ON CONFLICT … DO UPDATE … WHERE`). It guarantees an already-pending-and-fresh row is **not** re-kicked, and `cur.rowcount` is then the authoritative "did I win the kick?" signal — so **at most one daemon thread is spawned per record** even under two near-simultaneous POSTs (closes the TOCTOU gap the draft acknowledged but did not fully fix). Express the staleness predicate however reads cleanly against the stored ISO8601 `created_at` (e.g. compare to `_now_iso()` minus `STALE_PENDING_MIN` in Python and pass a literal cutoff), rather than the pseudo-`datetime('now', …)` shown above.

**Explicit retry / fall-through map (added per critic — make intent unmissable):**
- `status == 'ready'` → return 200 cache hit. **Never re-dispatch.**
- `status == 'pending'` & fresh → 202, no new thread (dedup).
- `status == 'pending'` & stale (>5 min) → retryable (worker died mid-gen). Re-kick.
- `status == 'failed'` & `retry_count >= RETRY_CAP` → 200 terminal `{status:'failed', terminal:true}`. **Never re-dispatch.**
- `status == 'failed'` & within cooldown → 200 `{status:'failed', cooldown:true}`. No re-kick this click.
- `status == 'failed'` & under cap & past cooldown → **deliberate fall-through to upsert→pending→re-kick (retry).**
- no row → insert→pending→kick.

`_build_prompt` is re-run on every retry **by design** (source text may have been re-ingested) — this is intentional, not a leak.

### 3.4 Background generation thread (mirror `routes/competition.py:88-100` daemon pattern)

`session` is **request-scoped and unavailable in the spawned thread** (G.A.V.E.L. finding) — the `access_token` string and the prebuilt `prompt` are passed in as args. The thread opens its **own** `get_db()` connection. Spawning goes through `_spawn_generation` which acquires the **global generation semaphore** (§6) so a burst of distinct uncached records cannot spawn unbounded concurrent 90s `requests.post` calls against the 2-worker app.

```python
def _generate(content_type, source_id, prompt, access_token):
    capability = "legal_summary"   # in VALID_CAPABILITIES on both sides (chat.py:38 + gavel_dispatch.py:60)
    text, model = None, None
    error = None
    transient = False              # distinguishes retryable (timeout/502/queued) from terminal (unparseable/no-source)
    try:
        r = requests.post(
            f"{BRIDGE_URL.rstrip('/')}/api/gavel/dispatch",
            json={"capability": capability, "prompt": prompt},
            headers={"Authorization": f"Bearer {access_token}",
                     "Content-Type": "application/json"},
            timeout=90)
        if r.ok:
            body = r.json() or {}
            text = (body.get("response") or "").strip()   # OUTPUT FIELD = "response"
            model = body.get("model")
            # --- COLD-MODEL / QUEUED DETECTION (see §3.5) ---
            # If the hub ENQUEUED (cold mistral:7b) rather than blocking to completion,
            # 'response' is empty but there is NO error and the body signals a queue.
            queued = (not text) and (
                body.get("queued") is True
                or body.get("status") in ("queued", "pending", "running")
            )
            if queued:
                # KEEP the row 'pending' so the existing poll continues — do NOT mark 'failed'.
                _mark_pending_again(content_type, source_id, transient=True)
                return
            if not text:
                error = "Empty response from G.A.V.E.L."
                transient = True   # empty-but-no-error is treated as retryable, not permanent
        else:
            error = f"Hub error {r.status_code}"
            transient = r.status_code in (429, 502, 503, 504)   # circuit-open / saturation = retryable
    except requests.exceptions.Timeout:
        error = "Hub timeout (cold load) — retry"
        transient = True
    except Exception as exc:
        error = f"Dispatch failed: {exc}"
        transient = False

    parsed = _parse_gavel_json(text) if text and not error else None
    if text and not error and parsed is None:
        # got real output but it would not parse → guilt-token guard then terminal-ish failure
        pass   # parsed is None → failed branch below; NOT transient (unparseable is permanent-ish, capped)

    # --- Post-generation defamation guard (§4.4) BEFORE writing 'ready' ---
    if parsed is not None and _has_unsupported_guilt_assertion(parsed):
        parsed = None
        error = "Blocked: guilt-asserting language without source grounding"
        transient = False

    conn = get_db()
    try:
        if parsed:   # ready ONLY on a real, non-empty, parseable, guard-passing artifact
            conn.execute(
                "UPDATE ai_summaries SET status='ready', plain_summary=?, "
                "precedent_impact=?, key_points=?, model_used=?, generated_at=?, "
                "error=NULL, last_attempt_at=? "
                "WHERE content_type=? AND source_id=?",
                (parsed["plain_summary"], parsed["significance"],
                 json.dumps(parsed["key_points"]), model, _now_iso(), _now_iso(),
                 content_type, source_id))
        else:        # cache the FAILURE — never a blank "success"; bump retry_count
            conn.execute(
                "UPDATE ai_summaries SET status='failed', error=?, generated_at=?, "
                "last_attempt_at=?, retry_count=retry_count+1 "
                "WHERE content_type=? AND source_id=?",
                (error or "Unparseable G.A.V.E.L. response", _now_iso(), _now_iso(),
                 content_type, source_id))
        conn.commit()
    finally:
        conn.close()
```

`BRIDGE_URL = os.getenv("LEGAL_BRIDGE_URL", "http://100.64.0.4:3000")` — copy from `chat.py:32` (the env-var line; `chat.py:36` is inside the `VALID_CAPABILITIES` set, not the URL). **Never** the public CDN hostname (60s cap).

### 3.5 Dispatch request/response shape (verified `routes/chat.py:69-77` + G.A.V.E.L. / hub findings)

- **Request:** `POST {BRIDGE_URL}/api/gavel/dispatch`, headers `Authorization: Bearer <access_token>`, `Content-Type: application/json`, body `{"capability": "legal_summary", "prompt": "<text>"}`. Omit `system` → hub auto-injects G.A.V.E.L.'s `agents.system_prompt` persona. `prompt` truncated server-side to 16000 chars. The actual `requests.post` precedent is `chat.py:69-77`.
- **Response (200, completed):** `{"response": "<model output>", "agent":"G.A.V.E.L.", "agent_id":147, "model":"mistral:7b", "department":"Legal & Regulatory", "duration_ms":..., "cost":0.0, "user":...}`. **Output field is `response`** (not `result`/`text`/`content`).
- **Errors:** hub returns 502 `{error,...}` on dispatch failure; 401 `{error}` on bad Bearer; 400 `{error:"prompt required"}` on empty prompt.
- **`json_mode`/`model` are SILENTLY DROPPED at the hub (verified, resolved — was Open Q2).** `gavel_dispatch.py` `dispatch_gavel()` (lines 137-141) forwards ONLY `capability`, `prompt`, `system_prompt` to `department_dispatcher.dispatch()`. It does **not** forward `model` or `json_mode` from the request body, even though its docstring (line 21) lists `model`. **Therefore the plan does NOT rely on `json_mode`** — JSON adherence is enforced by prompt engineering + the forgiving `_parse_gavel_json` extractor (§4). Setting `json_mode` from Legal Watch would do nothing; making it effective would require editing `gavel_dispatch.py` to forward it, which is **out of scope**.
- **⚠️ COLD-MODEL / QUEUED PATH — HARD PHASE-2 GATE (was a load-bearing assumption, now an explicit gate).** The whole "single sync dispatch is safe" premise depends on `/api/gavel/dispatch` returning a **completed** inference. But the hub path → DHQ `request_work()` **can ENQUEUE** and return a queue handle (e.g. `{queued:true}` / `{status:"queued"}` / empty `response`) when the target model (`mistral:7b`) is **COLD**, instead of blocking ~90s for the answer (verified pattern, KB #269301 "queued≠failure", #270002 delegation layer-3). `chat.py` — the cited precedent — returns the hub payload **verbatim and never inspects for a queued state**, so it does NOT prove the dispatch is synchronous.
  - **Phase-2 gate (do before generalizing):** empirically confirm what `/api/gavel/dispatch` returns for a **cold** `mistral:7b` — does it block to completion, or return a queue handle?
  - **Mitigation already wired (§3.4):** `_generate` explicitly detects an empty-`response`-but-no-error body carrying a queued/pending/running signal and **keeps the row `pending`** (via `_mark_pending_again`, transient) so the existing 3s poll continues — it is **NOT** recorded as `failed`. This prevents a cold first-view from being mis-cached as a failure. If the empirical test shows the hub can return a queue handle that the poll cannot resolve within the timeout, escalate to one of: (a) `_generate` re-polls the hub/queue until the model warms (bounded by 90s), or (b) request a hub-side synchronous flag (out of current scope). **Do NOT rely on `response` being populated on first cold dispatch.**

### 3.6 Failure → `status='failed'` caching + bounded retry policy

- A timeout / 502 / empty / unparseable / guard-blocked response → row persisted as `status='failed'` with `error` text and `retry_count` incremented. **Honesty rule** (KB #272631, #274925): never write `ready` for a blank/cold/queued result. A **queued/cold** body is the one exception that stays `pending`, NOT `failed` (§3.5).
- **Bounded retry (added per critic — the draft's retry was unbounded):**
  - `retry_count` (cap `RETRY_CAP=3`) + `last_attempt_at` (cooldown `RETRY_COOLDOWN_SEC=60`) live on `ai_summaries`.
  - On a `failed` row, the next `POST /api/summarize` re-kicks **only if** `retry_count < RETRY_CAP` **AND** `now - last_attempt_at > cooldown`. This prevents every user click on a structurally-unparseable record from re-burning a dispatch, and prevents hammering the hub during the very circuit-breaker saturation we cite (KB #275428).
  - **Transient vs permanent:** `timeout / 502 / 503 / 504 / 429 / empty` → retryable (counts toward cap but is the expected transient case). `unparseable JSON after prompt-tuning / guard-blocked / no source text` → effectively permanent; it still increments `retry_count` and reaches the cap quickly, after which the row is **terminal `failed`** and the UI shows "summary unavailable" (no further dispatch).
  - **Stuck-`pending` recovery:** a `pending` row older than `STALE_PENDING_MIN=5` min (gunicorn worker recycled mid-generation) is treated as retryable on the next POST, so a record cannot be permanently blocked in `pending` (closes the gap the draft's policy did not cover — it only handled `failed`).
- **Owner force-regen** (`POST /api/summarize/regenerate`) resets `retry_count=0` and bypasses cap/cooldown — the manual escape hatch for a terminal row.
- No automatic background retry (out of scope; on-demand only).

## 4. Prompt design — per content type, structured JSON out

All three prompts instruct G.A.V.E.L. to return **strict JSON** with exactly three keys so the parser is uniform:

```json
{"plain_summary": "...", "significance": "...", "key_points": ["...", "..."]}
```

**JSON adherence (resolved up front — was Open Q2):** `json_mode` is dropped at the hub (§3.5), so we cannot force `format=json` on Ollama. Adherence rests entirely on (a) explicit prompt instructions and (b) a tolerant parser. The plan does NOT gate `ready`/`failed` on the model being perfectly well-behaved — see parser tolerance below.

### 4.0 `_parse_gavel_json(text)` — tolerance spec (pinned, added per critic)

The parser is the gate between `ready` and `failed` for ALL three content types, so its tolerance is specified precisely, not left to chance:

1. **Fence stripping:** strip ```` ```json ```` / ```` ``` ```` fences and any leading/trailing prose; extract the first balanced `{ … }` block.
2. **`json.loads`** the extracted block.
3. **Key aliasing / normalization:** accept near-miss keys and normalize — `plain_summary` ← `summary` / `plain` / `plainSummary`; `significance` ← `precedent_impact` / `impact` / `precedent`; `key_points` ← `keyPoints` / `points` / `bullets`. Map the canonical `significance` → `ai_summaries.precedent_impact`.
4. **Coerce `key_points`** to a list (split a string on newlines/`;` if the model returned prose; cap at 5 items — §4.5).
5. **Plain-text fallback (do NOT hard-fail a usable answer):** if no JSON block is extractable but `text` is non-trivial prose, store the raw text as `plain_summary`, `significance=""`, `key_points=[]`, and still mark `ready` — a readable summary is better than a `failed` row. ONLY truly empty/garbage output falls through to `failed`.
6. On total failure (empty / unusable) → return `None` → row cached as `failed` (§3.4), counting toward `RETRY_CAP`.

This tolerance — plus the bounded retry cap — is what prevents a near-miss model response from becoming an infinite manual-retry sink.

### 4.1 SCC decisions (`_build_prompt(conn,'scc',id)`)

Source columns (verified `schema.sql:79-91`): `case_name`, `citation`, `decision_date`, `summary` (≤500-char RSS description), `areas_of_law` (JSON). **`outcome`, `panel_size`, `majority_author` are frequently NULL** and there is **NO full judgment text** — summarize ONLY the provided metadata/abstract. Note: `scc_decisions.outcome` carries a CHECK constraint (`schema.sql:85`: `CHECK(outcome IN ('allowed','dismissed','varied', NULL))`) — the summarizer only *reads* `outcome`, never writes it, so the constraint never interferes; it simply reinforces that `outcome` is one of those 3 values or NULL (and is "often NULL" as stated).

Prompt skeleton:
> You are summarizing a Supreme Court of Canada decision for a public legal-intelligence product. Use ONLY the metadata provided below — do NOT invent reasoning, holdings, votes, or outcomes not present in the text. Describe only the court's own stated outcome; if the outcome is not stated, say the outcome is not specified. Do not assert wrongdoing by any party. Keep `plain_summary` and `significance` to ≤3 sentences each and `key_points` to ≤5 items. Return strict JSON `{plain_summary, significance, key_points}`. `significance` = neutral note on why the case may matter (area of law, novelty) grounded only in the abstract; if you cannot ground it, say so.
> Case: {case_name} · Citation: {citation or "n/a"} · Date: {decision_date} · Areas: {areas_of_law} · Abstract: {summary or "(no abstract)"}

### 4.2 Regulations (`_build_prompt(conn,'regulation',id)`)

Source columns (verified `schema.sql:17-28`): `title`, `gazette_part`, `reg_type`, `published_date`, `description` (≤500 chars). **`department` is empty for 100% of rows** and `description` is often boilerplate Gazette masthead text — rows are Gazette *issues*, not individual regulations (regulations finding). Prompt must tolerate thin input.

Prompt skeleton:
> You are summarizing a Canada Gazette publication entry. Use ONLY the title and description provided; they may be brief or generic. Do not invent regulatory content not present. If the description is generic publication boilerplate, say so plainly in `plain_summary` and keep `significance` factual ("a {reg_type} item in {gazette_part}, {published_date}"). Keep `plain_summary`/`significance` to ≤3 sentences each, `key_points` to ≤5 items. Return strict JSON `{plain_summary, significance, key_points}`.
> Title: {title} · Part: {gazette_part} · Type: {reg_type} · Date: {published_date} · Description: {description}

### 4.3 Ethics rulings (`_build_prompt(conn,'ethics',id)`) — DEFAMATION-CRITICAL

Source columns (verified `schema.sql:46-60`): `report_name`, `subject_full_name`, `subject_role`, `report_type` ('act'|'code'), `ruling_date`, `finding` (**NULL in practice** — verdict lives in PDF, not extracted), `finding_summary` (CIEC's verbatim Description, ≤700 chars, **may be NULL**).

⚠️ **The list endpoint `GET /api/ethics` does NOT return `subject_full_name`, `subject_role`, or `report_pdf_url`** (`ethics.py:42-47`). The summarize handler must **fetch the row itself by `id`** (`SELECT * FROM ethics_rulings WHERE id=?`) to get the full safe column set — do not trust the client to pass them.

**Hard NULL guard:** if `finding_summary` is NULL/empty → `_build_prompt` returns `None` → endpoint returns `{status:"unavailable"}`, NO dispatch, NO generation. Do not synthesize from name/role.

Prompt skeleton (defamation-safe):
> You are summarizing a published Conflict of Interest and Ethics Commissioner (CIEC) report. Summarize ONLY the Commissioner's published Description below. Attribute everything to the report ("The Commissioner's report describes…"). State that this is an examination/inquiry under the {COI Act | Code for Members} — a process, not a proven offence — unless the Description itself states a conclusion. Do NOT assert, imply, or speculate that the subject is guilty, broke the law, "violated" rules, or committed wrongdoing beyond what the Description itself concludes. There is no asserted verdict (finding is unrecorded) — do not invent one. Do not editorialize, add outside facts, or characterize the person. Use the published name/role neutrally. Keep `plain_summary`/`significance` to ≤3 sentences each, `key_points` to ≤5 items. Return strict JSON `{plain_summary, significance, key_points}`; `significance` = neutral note on the nature of the report only.
> Subject: {subject_full_name} ({subject_role or "role n/a"}) · Report type: {report_type} · Date: {ruling_date or "n/a"} · Published description: {finding_summary}

### 4.4 Post-generation defamation guard (added per critic — automated backstop, not just human review)

Because the prompt injects `subject_full_name`/`subject_role` and a model can still produce a defamatory characterization despite instructions, `_has_unsupported_guilt_assertion(parsed)` runs **before** any row is marked `ready` (§3.4):

- Lexically scan `plain_summary` + `significance` for guilt-asserting tokens: `guilty`, `broke the law`, `violated`, `wrongdoing`, `convicted`, `committed an offence`, `found to have breached` (case-insensitive).
- If any such token appears **and is not grounded** in the source `finding_summary` (i.e., the token/its stem is absent from the source Description), the summary is **rejected**: `parsed → None`, `status='failed'`, `error="Blocked: guilt-asserting language without source grounding"`. The record then shows "summary unavailable" rather than a defamatory `ready` summary.
- This is a **launch safety net** layered on top of SOLO+ gating + the Phase-5 manual review of generated samples — not a replacement for them.

### 4.5 Output length bounding (added per critic)

All three prompts cap `plain_summary`/`significance` at ≤3 sentences and `key_points` at ≤5 items (above). This bounds render size and keeps generation latency under the 90s timeout. Input prompts are all **<< 16000 chars** for these three thin content types, so the server-side 16000-char truncation is moot for input — it cannot clip the source text in practice.

### 5.4 Loading / poll / error / XSS states

- **Loading:** detail row shows "G.A.V.E.L. is analyzing this {record} — this can take up to ~90s on first view" (textContent).

  - A transient `5xx`/network error → **continue** polling until the cap (do not hard-stop on one blip).
  - At the cap with no `ready` → show a "Try again" button (re-POST).
  This prevents `API.get` throwing inside the loop from silently killing the poll.
- **Error / failed:** retryable `failed` → show `error` text + a "Retry" button (re-POST; honors cap/cooldown — §3.6). Terminal `failed` (`terminal:true`) → show "Summary unavailable for this record" with NO retry button.

- **XSS (MANDATORY):** all rendering via `document.createElement` + `el.textContent` (or `el.textContent=''` to clear). **Never `innerHTML`** with record/AI content. `key_points` rendered as a `<ul>` of `<li>` each set via `textContent`. ## 6. Concurrency / welfare / cost

- **Bounded by construction (per-record):** on-demand+cache means **one G.A.V.E.L. dispatch per uncached record**, triggered by a deliberate user click. There is no loop, no fan-out, no batch. The dispatch runs in a daemon thread, never on the gunicorn request worker.
- **Bounded per-process (added per critic — close the burst gap):** legal-watch runs `gunicorn --workers 2` (KB #273438/#273424). The 90s dispatch is correctly off the request thread, so request workers aren't blocked — but a **burst of distinct uncached records** (many users, many rows) could otherwise spawn **unbounded** daemon threads each holding a 90s `requests.post`. Fix: `_spawn_generation` acquires a **module-level `threading.BoundedSemaphore(MAX_CONCURRENT_GENERATIONS)`** (default 3) before starting `_generate`; if the semaphore is exhausted, the row stays `pending` and the user's poll continues until a slot frees (or the POST returns 202 and a later click re-kicks). This caps concurrent 90s hub calls per process regardless of click volume.
- **Duplicate-concurrent guard (hardened — was a benign TOCTOU caveat, now closed):** the conditional `ON CONFLICT … DO UPDATE … WHERE status != 'ready' AND NOT (fresh pending)` plus `cur.rowcount` as the "did I win the kick?" signal (§3.3) guarantees **at most one daemon thread per record** even under two near-simultaneous POSTs — not merely "at most one row." Two users (or a double-click) clicking the same uncached row produce exactly one in-flight dispatch.
- **Welfare/replacement inherited free:** all inference routes through the hub `/api/gavel/dispatch` → DHQ orchestration engine, which already welfare-gates G.A.V.E.L. and swaps in a substitute if over-stressed (KB #258625). Legal Watch does **not** reimplement welfare.
- **Cost:** cloud escalation is globally OFF (`platform_settings.escalation_mode='local_only'`, ADR-004 / KB #269301) — summaries stay on local `mistral:7b`, near-zero marginal cost. `response.cost` is `0.0`. The hub per-node circuit breaker (KB #275428) will refuse rather than thrash under saturation → handled as a retryable `failed` row (§3.6), and the retry cooldown means clicks during saturation don't amplify load.
- **Failed-row visibility (added per critic):** so silent failures across many records don't go unnoticed (the "green job zero artifact" family — KB #273381/#258307), the owner force-regen endpoint also returns a count of `status='failed'` rows, and §8 verify step 9 checks it. A minimal `GET /api/summarize/regenerate` (or a tiny `?stats=1` on it) surfaces `{failed_count, terminal_failed_count}` for owner triage.
- **Future (OUT OF SCOPE):** an optional nightly pre-gen of summaries for new records. That would be a **batch** workload and therefore MUST NOT use sync dispatch from a request path (KB #275739). It would require the async-fleet path: a scheduler job (`digest/scheduler.py`) enqueuing one background dispatch per record with throttling, or DHQ delegation. Explicitly excluded here per locked decision #2.

## 9. Risks & gotchas

| Risk | Mitigation |
|---|---|
| **#275739 sync-batch trap** — looping sync dispatch on the web thread blocks gunicorn workers → 503s. | On-demand+cache = **one dispatch per record, in a daemon thread**, never on the request path. Single sync-shaped dispatch is allowed (chat.py precedent). No batch in scope. |
| **gunicorn worker blocking** | The request handler returns 202 immediately; only the daemon thread holds the 90s dispatch. Request worker (2 workers) is never blocked. |
| **Unbounded daemon threads under burst** | Module-level `BoundedSemaphore(3)` caps concurrent 90s hub calls per process (§6); excess records stay `pending` and poll until a slot frees. Per-process bounding, not just per-record. |
| **Cold-load `mistral:7b` returns a QUEUED handle (not completed)** | `_generate` detects empty-`response`-no-error + queued/pending/running signal → KEEPS the row `pending` (NOT `failed`) so the poll continues (§3.5). **Phase-2 gate:** empirically confirm the cold-dispatch path; chat.py does not prove synchronicity. |
| **Cold-load / 90s timeout UX** | First-view summary may take tens of seconds (mistral:7b cold). UI shows a clear "analyzing… up to ~90s" state + poll + retry. Timeout → retryable `failed` → bounded retry on next click. |
| **Unbounded retry hammering the hub** | `retry_count` (cap 3) + `last_attempt_at` cooldown (60s) (§3.6); over-cap rows go terminal `failed` (no further dispatch); transient (timeout/502/queued) vs permanent (unparseable/no-source) distinguished. |
| **Stuck `pending` (worker recycled mid-gen)** | `pending` older than 5 min is treated as retryable on next POST (§3.3/§3.6) — a record can't be permanently blocked in `pending`. |
| **JSON adherence of mistral:7b** | `json_mode` is **dropped at the hub** (verified, §3.5) — not relied on. `_parse_gavel_json` tolerance spec (§4.0: fence-strip, key-alias, coerce, plain-text fallback) + retry cap prevents near-miss output becoming an infinite retry sink. |
