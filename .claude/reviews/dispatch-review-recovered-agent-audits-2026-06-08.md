## Audit 1: Dispatch Queue + model_dispatch_worker (dispatch_pending_queue drain)

**How it works:**

The dispatch queue is drained by `model_dispatch_worker()` (platform_v2/services/model_dispatch_service.py:1208), registered as an APScheduler IntervalTrigger job at **15s** (ai_bridge/agent_loop.py:966, `max_instances=1, coalesce=True`) — NOT the 30s the skill/CLAUDE.md docs claim (stale). Each cycle:

1. `reconcile_fleet_models()` (line 262, throttled to 60s) probes each online node's live `/api/tags` over mesh, makes `node_ollama_models`/`remote_nodes.extra_capabilities.ollama_models` the truth, and submits tier-gated re-pulls of vanished models into `_CPU_EXECUTOR`.
2. `_expire_stale_tasks()` (line 1140) flips `queued` rows past `expires_at` → `expired`, firing delegation-failure callbacks first (Layer-3 #269999 — correct).
3. `_get_all_warm_nodes_for_models()` (line 86) builds `{model: [node_id_or_None,...]}`. Hub warm models (`_get_warm_models_hub`, line 43, via `agent_models.get_loaded_models`) are inserted FIRST as `None`; then node rows from `node_ollama_models JOIN remote_nodes` (`is_available=TRUE`, heartbeat<3min, `ollama_available`) ordered `bridge_priority DESC, current_load ASC`, gated by `fleet_resource_router.can_node_run_model(row, name)` (fit-only, load-independent — #1518, present and correct at lines 139-149).
4. For each `(model, node)` pair, `_claim_tasks(model, limit)` (line 403) atomically claims up to MAX_TASKS_PER_MODEL=8 `queued` rows with `preferred_node_id IS NULL` via `FOR UPDATE SKIP LOCKED` ordered `priority DESC, queued_at ASC`, capped by MAX_TASKS_PER_CYCLE=20. Each claimed task is submitted to `_CPU_EXECUTOR` (ThreadPoolExecutor, max_workers=6, line 37) running `_execute_task(task, node_id)`.
5. `_execute_task` (line 786) resolves the node row, then calls `disp.ensure_model_ready(agent, model, {'hostname','port'})` (the #1516 dict fix — present/correct at line 861) as a readiness preflight; if not ready → `_requeue_cold` (line 507, sets status back to `queued`, bounded by `expires_at`). If ready → `disp._dispatch_to_node()` (node) or `disp._execute_llm()` (hub). Success → `_mark_done` (captures real node tokens, line 889); failure → `_mark_failed`.
6. Worker BLOCKS on `as_completed(futures, timeout=300)` (line 1266) before returning — so the 15s job can run up to 300s; APScheduler `coalesce=True`+`max_instances=1` means overruns collapse missed ticks.
7. `_claim_preferred_node_tasks(limit=4)` (line 439) drains node-pinned tasks (cold-load acceptable) only after warm drain.
8. If nothing executed, `_ensure_ram_for_model` + `ensure_model_ready` warms the highest-priority queued model for next cycle (line 1290).

`ensure_model_ready` → `ModelService.ensure_model_ready` (model_service.py:366) acquires a **single process-global `_MODEL_LOAD_LOCK`** (line 34/393, acquire timeout 150s) and holds it across the ENTIRE `_ensure_model_ready_locked` body — including `_fetch_ps` (5s) and `load_model` (line 249, `urlopen` timeout 600s). Tracking is intact: `_execute_task`→`_dispatch_to_node`/`_execute_llm` write `task_execution_log` (department_dispatcher.py:3822) — live-verified 538 writes/20min, all `success=true`, across wtf_*/agent_loop/fleet_warmup; queue `_mark_done` captures `result_tokens`/`result_node_id` (node 68 hub=2898 tok, node 127 UK=324 tok live).

**Findings:**

### [CRITICAL / broken] Global _MODEL_LOAD_LOCK serializes ALL fleet warm-boots — one slow CPU cold-load freezes every node's dispatch (contagious stall, confirmed live)
- **Detail:** ensure_model_ready (model_service.py:393) acquires ONE process-global threading.Lock (_MODEL_LOAD_LOCK, line 34) and holds it across the WHOLE _ensure_model_ready_locked body — _fetch_ps (5s timeout) + load_model (line 249, urlopen timeout 600s). The worker submits every claimed task into _CPU_EXECUTOR (6 threads, line 37); every _execute_task calls ensure_model_ready (lines 858 node / 906 hub) as a preflight. So all 6 pool threads contend on ONE lock. When ANY warm-boot is a slow CPU 7B/custom-model load, every other thread (and every other node's dispatch — hub, Starship, all 4 outposts, Citadel) blocks behind it for the FULL load duration, then up to 150s more before timing out to a re-queue. LIVE EVIDENCE: qwen25-classify cold-loaded on the hub in 275874ms (4.6 min) and 35630ms; qwen2.5:1.5b repeatedly 63-77s — each held the global lock the entire time. The lock is GPU-fragmentation protection but is mis-scoped: it serializes CPU loads and REMOTE-node loads against each other and against the hub, even though they touch independent hardware.
- **Evidence:** model_service.py:34 (_MODEL_LOAD_LOCK=Lock()), :393 (acquire timeout 150), :397-400 (held across _ensure_model_ready_locked incl. load_model urlopen timeout=600 at :277); model_dispatch_service.py:1258 (_CPU_EXECUTOR.submit per task) + :858/:906 (ensure_model_ready in every thread). LIVE: docker logs — 'qwen25-classify cold-loaded on host.docker.internal:11434 in 275874ms', multiple 'qwen2.5:1.5b cold-loaded ... 77351ms/72609ms'.
- **Fix:** Replace the single global lock with a PER-HOST lock keyed by ollama_url (dict of locks, e.g. defaultdict(Lock) under a small registry mutex). The GPU-fragmentation concern is real ONLY for concurrent loads onto the SAME GPU host — a per-host lock fully preserves that guarantee while letting hub, each Starship, and each outpost warm in parallel. Additionally: hold the lock ONLY around the load_model POST, not around _fetch_ps (the 'already warm' fast path needs no lock at all — check ps lock-free, acquire only if a load is actually required). This alone eliminates the contagious stall.

### [HIGH / broken] Hub is iterated first for every warm model → small CPU work piles onto the hub and cold-loads there instead of idle outposts
- **Detail:** _get_all_warm_nodes_for_models (line 101) seeds the result dict with hub models as `None` BEFORE appending node rows (line 150), and Python dict preserves insertion order. model_dispatch_worker iterates `for node_id in node_ids` (line 1249) hub-first, and _claim_tasks (line 403) has NO per-node pool partition — it drains the SAME global queued pool each iteration. So the hub claims the first batch (up to 8) of every model every cycle. For qwen2.5:1.5b — a small CPU model that should run on idle outposts — this pins it to the hub's slow Quadro/CPU where it cold-loads (22-77s, lock-serialized) while 4 idle nodes (UK load 0, Lithuania, Citadel, Starships) sit unused. The node-ORDER ranking (bridge_priority DESC, current_load ASC) is computed but wasted because hub (None) is hardcoded ahead of it and the broken current_load (Singapore=57, US=100) further corrupts the node ordering. The sync-path scorer score_node_for_model has best-hardware/anti-hub-for-small-models logic; the QUEUE worker has none — it just takes hub first.
- **Evidence:** model_dispatch_service.py:101 ({m:[None] for m in hub_warm} inserted first), :150 (result.setdefault(name,[]).append(row['id']) appended after), :1249 (for node_id in node_ids — hub None first), :403-431 (_claim_tasks: no node filter on the queued pool). LIVE: qwen2.5:1.5b is is_available on 8 nodes incl. UK(load0)/Citadel/Starships, yet all recent cold-loads are 'on host.docker.internal' (hub). current_load live: Outpost-US=100, Singapore=57 (broken counter corrupting node order).
- **Fix:** Order node_ids so that for a CPU-only (not prefer_gpu) model the hub is LAST (failover), and for prefer_gpu the fastest-GPU node is first — reuse fleet_resource_router scoring instead of raw dict order. Prefer claiming for a warm-and-LOADED node (live /api/ps) over a warm-but-PULLED hub that would cold-load. Round-robin or score-rank node_ids before the claim loop so idle outposts get the small-model batches.

### [HIGH / broken] current_load counter is broken (drift to 100) and still drives the sync-path node scorer + node ordering — capable idle nodes get deprioritized/skipped
- **Detail:** remote_nodes.current_load is incremented (fleet_node_routes.py:2513) but decrement is skipped on error paths (:2558), and a different-scale writer in ai_bridge/node_router.py:264 adds +5/caps-100. Outpost-US at 100 is effectively load-fenced from sync routing despite being idle.
- **Evidence:** fleet_resource_router.py:183 (cur_load=max(int(current_load),0) in score_node_for_model), :215, :350; model_dispatch_service.py:126 (ORDER BY rn.current_load ASC). - **Fix:** Stop trusting current_load as a load signal. Either (1) derive live load from `dispatch_pending_queue` running-count per node + node /api/ps, or (2) make current_load self-healing: a periodic reconcile that recomputes it from running queue rows (mirror reconcile_task_counters' canonical 'active work' filter). Until then, drop current_load from BOTH the queue ORDER BY and score_node_for_model's load term (or clamp its weight near zero). Add a fleet-wide reset job. This is the same class as the report's #2.

### [HIGH / optimization] Warm sets are reactive — nothing keeps a node's target models resident, so cold-loads (and via the global lock, stalls) recur indefinitely
- **Detail:** Models load on dispatch (ensure_model_ready) and evict on Ollama KEEP_ALIVE (hub 30m, nodes 10m). The worker's only proactive warm step is the bottom-of-cycle 'load highest-priority queued model' (line 1290) and ONLY when total_executed==0 — it never maintains a stable resident warm SET per node. node_provisioning.recommend() computes ideal warm sets but nothing enforces them. This converts the fleet from reactive-cold to proactive-warm and removes the cold-load events that trigger the global-lock stall.

### [MEDIUM / risk] Worker blocks up to 300s on as_completed — a slow batch monopolizes the single-instance job and delays expiry/reconcile/new claims
- **Detail:** model_dispatch_worker waits on as_completed(futures, timeout=300) at line 1266 (and again at :1282 for preferred tasks) BEFORE returning. Run _expire_stale_tasks + reconcile_fleet_models at the TOP of every cycle unconditionally so they fire even while prior batches are in flight. This restores the true 15s cadence and lets ready warm models drain while a slow load completes in the background.

**Findings:**

### [CRITICAL / broken] Global _MODEL_LOAD_LOCK serializes EVERY node's warm-boot — one slow CPU-7B cold-load stalls the whole fleet
- **Detail:** _MODEL_LOAD_LOCK (model_service.py:34) is a single process-global threading.Lock. ensure_model_ready acquires it (line 393, 150s acquire timeout) and HOLDS it for the entire _ensure_model_ready_locked, including the load_model urlopen with a 600s timeout (model_service.py:277). Because target_host now flows through the same lock (post-#1517), a cold CPU-7B load on Citadel (~84s, confirmed live: Citadel is running qwen2.5:7b on CPU vram=0) blocks the preflight of EVERY other node's dispatch — hub, Starships, all outposts — for that whole duration. The model_dispatch worker submits _execute_task to a thread pool (model_dispatch_service.py:1258); each thread calls ensure_model_ready and contends on this one lock. The lock's stated purpose (line 29-31) is preventing CONCURRENT GPU CUDA graph_reserve fragmentation on the HUB GPU — it was never meant to serialize independent remote hosts that each have their own Ollama + their own GPU/CPU.
- **Evidence:** model_service.py:34 (_MODEL_LOAD_LOCK = _threading.Lock(), module-global); :277 (urlopen timeout=600 while lock held); :393 (acquire(timeout=150)); :470 (load_model called inside lock for node target). Live: docker exec model_service._fetch_ps('http://100.64.0.10:11434') -> CITADEL running qwen2.5:7b size_vram=0 size=4.6GB (CPU 7B = the ~84s holder). Worker submits parallel _execute_task threads: model_dispatch_service.py:1258.
- **Fix:** Replace the single global lock with a PER-HOST lock map keyed by ollama_url, guarded by a small meta-lock: `_host_locks: Dict[str, Lock]` with `_locks_guard`. Acquire the per-host lock inside _ensure_model_ready_locked AFTER resolving ollama_url. This is correct: CUDA graph_reserve contention is per-GPU/per-Ollama-instance, so per-host serialization preserves the safety property while letting Citadel, hub, and Starships warm in parallel. Keep a short acquire timeout per host. This is the #1 fleet-stall fix and directly enables proactive warm sets (Finding 6) without contagion.

Live proof: Outpost-US shows current_load=100 right now; score_node_for_model for qwen2.5:1.5b (a model it CAN run, fit=True) returns score=None at load=100 (penalty -10 drives score negative), vs 1.8 at load=0. - **Evidence:** remote_nodes live: outpost_us_001 current_load=100 (fresh=t). docker exec score test: load=0 ->1.8, load=10 ->0.8, load=100 ->None for qwen2.5:1.5b on US. Reset current_load=0 fleet-wide now (the session claimed this but US=100/Citadel=2/UK=1 prove it did not stick — a writer is re-inflating).

### [MEDIUM / risk] Bug-B fix (load_model node-aware) is correct, but remote load has NO capacity check — a too-large model can OOM/thrash a node
- **Detail:** #1517 correctly made load_model warm the TARGET host (model_service.py:264, base=ollama_url) and made ensure_capacity hub-only (model_service.py:451-465). ### [CRITICAL / broken] GLOBAL _MODEL_LOAD_LOCK serialises model loads across ALL hosts — a slow CPU cold-load freezes the entire fleet's dispatch

### [MEDIUM / optimization] ADR-017 parallel drain has NO speed weighting — splits a model's work equally across fast GPU and slow CPU warm nodes
