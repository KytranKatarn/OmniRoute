# Broker consumer implementation boundary

This adds a diagnostic consumer for the broker merged by #3795. It does not
connect a running worker, provision a socket/key, enable supervised execution,
or change replacement admission. There are no route, scheduler or startup hooks.

`services.codex_stop_receipts.verify_current_receipt` independently checks exact
canonical bytes, strict types, RSA-4096/PSS/SHA-256 signatures, the reviewed issuer
pin, expected assignment identity, the signed durable assignment seal and an exact
persisted completion. The broker's existing 300-second receipt age limit and
60-second future tolerance are enforced for compatibility. Expired evidence stays
unknown; no key is fetched or regenerated by verification. Missing cryptography
support returns `crypto_unavailable`; this change installs no dependency.

`services.codex_broker_client.BrokerClient` is disabled by default. Explicitly
configured callers can only request `get_journal` for one assignment. The client
checks socket and parent ownership/permissions plus actual `SO_PEERCRED`, applies
one bounded timeout across connect/send/read, half-closes the request (the broker
uses EOF framing), and caps response bytes, entry count and JSON depth. Transport
errors return sanitized unknown observations. No prompt, key, receipt or remote
error contents enter diagnostic codes. There are no assign/start/stop operations.

The caller must supply the issuer public-key pin from reviewed configuration and
the expected assignment from server-owned association state. Never obtain either
from the presented receipt, task metadata, user request, or untrusted projection.
Journal entries must come from a fresh authenticated broker read. Pins are explicit
values in this preparatory library; provisioning a persistent registry and exposing
this client to running platform code are separate steps.

Even a verified current receipt has `stop_confirmed=false` and
`recovery_eligible=false`. `evidence_verified` means only that diagnostic evidence
matches the configured key/assignment and current journal. It cannot certify the
approved [trusted-stop contract](repair-bay-trusted-stop-receipts.md): the broker's
current envelope lacks attempt/proposal/generation, signed issuer/host/boot/version
identities, full container/label/start reconciliation, reaping evidence, exact
publication disposition, journal sequence/previous digest and explicit outcome
states. A boolean `assignment_sealed` is not proof that future starts are fenced.
Real host observers, dedicated issuer isolation, containment and recovery remain
Host OpenCode work. Do not relax validation to bridge these missing guarantees.

Validation (pure tests deliberately bypass the global database fixture):

```sh
PYTHONPATH=platform_v2 python3 -m pytest --noconftest -q platform_v2/tests/test_codex_broker_consumer.py
```

Tests include the merged broker's actual handlers with temporary SQLite storage,
generated test-only keys and fake independent observers, plus an actual temporary
Unix socket exchange. No production datastore, service, key or inference is used.

The diagnostic verifier accepts the extended assignment seal introduced in #3801.
Full container ID, positive PID inventory, repository, and branch must match
independently supplied assignment context and remain covered by the signature.
Legacy seals cannot satisfy extended context. This enables no execution or recovery.
