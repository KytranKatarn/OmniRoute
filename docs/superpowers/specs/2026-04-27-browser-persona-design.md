# Browser Persona System — Design Spec
**Project**: #287 ARCHIE CLI — Playwright Web Automation Agent
**Date**: 2026-04-27
**Status**: Approved for implementation

---

## Vision

Give human agents (worker_type='internal') a real online presence. Each human agent becomes a digital identity — logged in on the web, capable of posting, engaging, editing profiles, and navigating platforms that don't expose APIs. Content is generated by S.I.G.N.A.L. and delivered by the agent's own browser session.

Long-term: human agents evolve into coordinated online participants — daily shares, interactions, and replies — or execute as a unified office marketing team with campaign-level coordination across LinkedIn, Twitter/X, and beyond.

---

## Design Principles

- **No parallel infrastructure** — browser skills extend Agent Academy, tasks route through Dept HQ dispatch, content from S.I.G.N.A.L., approvals via Telegram.
- **Human agents only** — `worker_type='internal'` exclusively. AI acronym agents never get browser credentials.
- **Extensible by default** — skill registry pattern (drop a file, restart). Not hardcoded.
- **Approach C from day one** — full persona (sessions + rules + skills), not just a task runner. Lv5 is the destination.

## What We Build Fresh

### 1. `archie_browser` Docker container

```
/mnt/archie_brain/archie-browser/
├── app.py                  # Flask HTTP API
├── skill_runner.py         # Discovers + executes skills
├── session_manager.py      # Encrypted session store, auto-refresh
├── skills/
│   ├── __init__.py
│   ├── linkedin_post.py
│   ├── linkedin_profile_edit.py
│   ├── twitter_post.py
│   ├── meta_portal_setup.py
│   └── web_form_fill.py
├── Dockerfile
├── docker-compose.yml
└── requirements.txt        # playwright, flask, cryptography, psycopg2
```

**HTTP API:**
```
POST /task
  body: { agent_id, skill, params: {}, wait: bool }
  returns: { task_id, status }

GET /task/:id
  returns: { task_id, status, result, error, duration_ms }

POST /session/setup
  body: { agent_id, platform, password, username }
  action: launches Playwright, logs in, saves session cookies

GET /session/:agent_id/:platform
  returns: { status: active|expired|missing, last_used }

POST /session/:agent_id/:platform/refresh
  action: re-auth using stored password, refresh session cookies
```

**Skill interface** — every skill file implements:
```python
SKILL_NAME = "linkedin_post"
PLATFORMS = ["linkedin"]

async def execute(page, params: dict) -> dict:
    # page is an authenticated Playwright page for the agent's session
    # params: content, hashtags, etc.
    # returns: { success, result, screenshot_path }
```

Container discovers all `skills/*.py` files at startup. Adding a skill = drop a file, restart.

### 2. Database Tables

```sql
-- Encrypted browser sessions per agent per platform
CREATE TABLE agent_browser_sessions (
    id SERIAL PRIMARY KEY,
    agent_id INTEGER NOT NULL REFERENCES agents(id),
    platform VARCHAR(50) NOT NULL,           -- linkedin, twitter, facebook, etc.
    username VARCHAR(255),
    password_encrypted TEXT,                  -- AES-256, key from env
    session_data_encrypted TEXT,              -- Playwright storageState JSON, encrypted
    session_expires_at TIMESTAMPTZ,
    status VARCHAR(20) DEFAULT 'missing',     -- missing, active, expired, error
    last_used_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(agent_id, platform)
);

-- Online persona rules per agent
CREATE TABLE agent_online_persona (
    id SERIAL PRIMARY KEY,
    agent_id INTEGER NOT NULL REFERENCES agents(id) UNIQUE,
    posting_frequency VARCHAR(20) DEFAULT 'weekly',  -- daily, weekly, manual
    preferred_tone VARCHAR(20) DEFAULT 'professional',
    active_platforms JSONB DEFAULT '[]',              -- ["linkedin", "twitter"]
    topic_interests JSONB DEFAULT '[]',               -- ["AI", "business", "tech"]
    engagement_rules JSONB DEFAULT '{}',              -- likes, comments, follows rules
    campaign_id INTEGER REFERENCES browser_campaigns(id),  -- NULL = solo, set = coordinated
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Task execution log
CREATE TABLE browser_task_log (
    id SERIAL PRIMARY KEY,
    agent_id INTEGER NOT NULL REFERENCES agents(id),
    skill VARCHAR(100) NOT NULL,
    platform VARCHAR(50),
    params JSONB,
    status VARCHAR(20) DEFAULT 'pending',     -- pending, running, completed, failed
    result JSONB,
    error_message TEXT,
    screenshot_path TEXT,
    triggered_by VARCHAR(50),                 -- schedule, telegram, event, cli
    duration_ms INTEGER,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ
);

-- Future: coordinated campaigns (Phase 2)
CREATE TABLE browser_campaigns (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    description TEXT,
    status VARCHAR(20) DEFAULT 'draft',       -- draft, active, paused, completed
    campaign_type VARCHAR(50),                -- marketing, product_launch, awareness
    target_platforms JSONB DEFAULT '[]',
    schedule JSONB,                           -- cron or one-time
    content_brief TEXT,                       -- S.I.G.N.A.L. uses this to generate per-agent content
    participating_agent_ids JSONB DEFAULT '[]',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

## Credential Flow

```
First-time setup (one-time manual step):
1. Admin enters username + password in DHQ Online Presence tab
2. archie_browser launches Playwright, navigates to platform login
3. Enters credentials, waits for 2FA prompt if needed
4. Admin completes 2FA in browser (shown via screenshot stream or real browser)
5. archie_browser saves storageState (cookies + localStorage) encrypted to DB
6. Session status → active

Daily operation (automatic):
1. Task arrives → session_manager loads storageState for agent+platform
2. Playwright restores session — no login needed
3. Skill executes
4. If session expired → auto re-auth using stored password
5. If 2FA triggered → Telegram alert to admin: "Kytran's LinkedIn needs 2FA"
```

## Phase 2 — Coordinated Marketing Campaigns

Once individual personas are stable, the campaign layer enables:

- **One brief → many posts** — S.I.G.N.A.L. generates per-agent variations of campaign content (same message, different voice per person)
- **Coordinated timing** — all agents post within a window (staggered, not simultaneous)
- **Cross-platform coverage** — Kytran on LinkedIn, another agent on Twitter, another on Facebook
- **Engagement coordination** — agents engage with each other's posts to amplify reach
- **Campaign analytics** — unified view of reach/engagement across all participating agents

The `browser_campaigns` table and `agent_online_persona.campaign_id` FK are scaffolded in Phase 1 to avoid a schema migration later.

## Phase 3 — Geographic Distribution

The fleet already has two nodes with distinct public IPs:

| Node | Location | IP | Identity |
|------|----------|-----|----------|
| Hub | Canada | 153.68.195.85 | Canadian presence |
| US Outpost | United States | 76.13.107.109 | American presence |
| Future nodes | Europe / Asia / etc. | TBD | Global coverage |

### Architecture

Each fleet node runs its own `archie_browser` container instance. The platform routes browser tasks to the node that matches the agent's `preferred_node`.

```
ARCHIE Platform
    │
    ├─→ archie_browser @ hub:4242       ← Canadian IP (153.68.195.85)
    │       Kytran Katarn posts from Canada
    │
    ├─→ archie_browser @ outpost:4242   ← US IP (76.13.107.109)
    │       US-based agents post from America
    │
    └─→ archie_browser @ node-eu:4242   ← European IP (future)
            EU agents post from Europe
```

### Schema Addition (Phase 3)

```sql
-- Add to agent_online_persona:
ALTER TABLE agent_online_persona
    ADD COLUMN preferred_node VARCHAR(50) DEFAULT 'hub',  -- hub, outpost-us, node-eu, etc.
    ADD COLUMN geo_label VARCHAR(100);                     -- "Toronto, Canada" — shown in DHQ
```

### Task Routing

`/api/browser/task` resolves the agent's `preferred_node` and forwards to the correct container:

```python
node_urls = {
    "hub":        "http://192.168.1.200:4242",
    "outpost-us": "http://76.13.107.109:4242",
}
container_url = node_urls.get(agent_persona.preferred_node, node_urls["hub"])
requests.post(f"{container_url}/task", json=payload)
```

### Why This Matters

- **Platform trust** — LinkedIn and Twitter track IP geolocation. Posts from diverse IPs look like a real distributed team, not a single-origin bot.
- **Rate limit isolation** — Each node has its own IP reputation. One node hitting a rate limit doesn't affect others.
- **Authentic presence** — A US-based agent genuinely posts from the US. A Canadian agent posts from Canada. Geolocation matches the agent's identity.
- **Scalability** — Adding a new geographic presence = spin up a VPS + deploy `archie_browser` + register node in the fleet. No platform code changes needed.

### Deployment

`archie_browser` is already containerized. Deploying to a new node is:
1. Add node to fleet (already handled by DHQ Fleet tab)
2. `docker compose up archie_browser` on the node (OTA push via fleet)
3. Set agent's `preferred_node` in DHQ Online Presence tab

The Stalwart mail server already acts as an outpost relay — this follows the same pattern.

## Security Notes

- `password_encrypted` and `session_data_encrypted` use AES-256, key from `BROWSER_ENCRYPTION_KEY` env var — never stored in DB
- `archie_browser` container is internal-only — no external port exposure, hub network only
- Platform proxies all browser tasks — external callers never reach container directly
- Browser tasks logged with `triggered_by` for audit trail
- AI agents blocked at dispatch layer (`worker_type != 'internal'` check before any browser task)
